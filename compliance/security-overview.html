1. Architecture

Help Me Breathe is a static website with a small number of serverless functions attached to it. There is no application server that stays running, no message queue, no cache layer and no admin panel. The only personal data stored anywhere is a subscriber's own account record — an email address, a sign-in identity, a plan and its dates. The attack surface is deliberately close to the smallest one a working product can have.

  • Static pages. Every page is a plain HTML file built ahead of time and served from a content delivery network. There is no server-side rendering, no template engine and no user input reflected into a page by a server.
  • Client-side JavaScript. The timer is native ES modules with no bundler, no framework and no third-party runtime dependencies at all. That means no dependency tree to be compromised through, and nothing to patch when a popular package is hijacked.
  • Serverless functions. A handful of endpoints under /api/ handle sign-in, the subscription lifecycle and the optional email list. They receive a JSON body and return a JSON response. They are written to the Web standard Request/Response interface, so they can be moved to another host without being rewritten.
  • Service worker. A service worker caches the pages and assets so the timer keeps working offline. It caches the application shell only. It never caches an API response and never stores anything about a session.
  • The embedded widget. A separate, versioned page under /embed/v1/ designed to be put in an iframe on someone else's site. It loads its own HTML, CSS and one script from helpmebreath.com and nothing else, from anywhere. A client session link at /s/ is a different page and is not held to that rule — see section 2.

2. Data flows

There are four flows in the whole system. Three of them concern the practitioner. None of them carries client data.

A person practises breathing.

browser → CDN: GET /box-breathing → HTML, CSS, JS. Then: nothing.

The session runs entirely in the page. Phase timing, cue tones and vibration are all local. Settings and session history are written to that browser's own local storage under the hmb. prefix and are never read by a server.

A client opens a co-branded session link.

browser → CDN: GET /s/?c=<base64url config> → HTML, CSS, JS
browser → Google Fonts: the site's typefaces. Then: nothing.

The entire configuration — technique, length, practitioner name, message, optional logo URL and subscription token — is encoded in the query string, so no server needs to remember it. The page decodes it in the browser. Every decoded field is written with textContent rather than as markup, only https image URLs are accepted, and the payload is length-capped, because this is attacker-controllable input rendered on our own domain.

This page differs from the embedded widget in one respect, and it is listed rather than glossed: it requests the site's typefaces from Google Fonts, so Google's font servers see the reader's IP address and user agent. Nothing about the session is sent with that request, and the page works if it is blocked. A practitioner's own logo, if the link carries one, is fetched by the reader's browser from the practitioner's own server. The widget under /embed/v1/ makes neither request.

A subscriber signs in.

browser → sign-in request { email } → a one-time link by email, or a Google sign-in · a short-lived signed token kept by the browser

There is no password at any point. A one-time email link, or a Google account, is exchanged for a short-lived signed token. An email address is never written to a log, an analytics event or an error report in full.

A white-label embed checks its entitlement.

iframe → entitlement check { token, host } → { active, host allowed }

The frame asks whether the token belongs to an active subscription, and sends the hostname of the page it is embedded in. The server answers for that hostname and no other, and the frame checks the same answer again before it changes anything on screen, so a token copied out of a public page's source is of no use on a site it was not issued for. If the check fails for any reason — an unreachable server, a lapsed subscription, a hostname that is not covered — the frame renders the free attributed widget rather than failing open.

There is no flow in which a client's name, contact details, health information or practice history reaches a server. The privacy attestation states this as a signed statement, and the Data Processing Addendum records it contractually.

3. Hosting, TLS and headers

  • The site is hosted on Vercel and served from its content delivery network. Vercel manages the TLS certificates and terminates TLS at the edge; plain HTTP requests are redirected to HTTPS, and www is redirected to the bare domain.
  • Secrets — the token signing key, the merchant of record's API key and webhook secret, and the email provider's key — exist only as encrypted environment variables in the hosting platform. They are not in the source repository, which carries a .gitignore entry for local environment files, and they are never logged.
  • Response headers set at the edge for every path: X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, and Permissions-Policy: camera=(), microphone=(), geolocation=().
  • X-Frame-Options: DENY is set on every path except the two that are meant to be embedded — the widget under /embed/ and the client session link at /s/ — which instead carry a Content-Security-Policy with frame-ancestors * because being embeddable is their purpose.
  • The serverless functions apply best-effort per-address rate limiting, and reject a request body that is larger or differently shaped than expected.
  • The Provider's accounts with the hosting platform, the domain registrar, the merchant of record and the email provider each use a unique password held in a password manager, with two-factor authentication enabled.

Part two

5. Accounts and the subscription token

There are no passwords. Signing in is a one-time email link or a Google account, so there is no credential store to leak. An account holds an email address, the sign-in identities used, the date it was created, the plan with its status and period dates, and the payment provider's subscription and customer identifiers. What the browser holds is a signed token, and that design choice is the reason a stolen token ages out on its own.

  • A sign-in is exchanged for a token of the form base64url(payload) + "." + base64url(HMAC-SHA256).
  • The payload carries a version, a subject reference, issue and expiry timestamps, and whether the subscription is active. It carries no name, no email address, no card data and nothing about anybody's practice.
  • Signing uses HMAC-SHA256 through the platform's WebCrypto implementation, with a secret held only in the hosting platform's environment. The signature is verified on the server, and that is what protects the things worth protecting: removing the attribution from a white-label embed, and the co-branded client session link. Be clear about what this does not do. In the browser the stored token is decoded but not verified, so what a person sees unlocked in their own browser is a convenience rather than a security boundary, and someone editing their own stored data can turn on the local conveniences without paying. Anything a practitioner actually sells — white-label attribution removal, class mode, co-branded links — is decided by the server, not by the browser.
  • Tokens are short-lived: 14 days. A cancelled subscription therefore expires on its own within a fortnight, with no revocation list to maintain and no action needed from anyone.
  • That 14-day life doubles as an offline grace period, so paid features keep working with no network and a practitioner in a room with poor signal is never locked out mid-session.
  • An account is for one person or one household. There is no device count and no domain count to administer, and no activation ledger to keep.
  • A sign-in link is single use and short-lived. Where a sign-in or a checkout returns someone to the site with a token in the address bar, the page removes it from the URL before anything else runs, and the analytics configuration is pinned to the path so a query string cannot reach it.

6. Accessibility posture

Real work has been done here, and no formal conformance claim is made. Both halves of that sentence are deliberate.

What has been done: the timer is fully operable from the keyboard, including starting, pausing, stopping and switching technique; phase changes are announced through an ARIA live region so a screen reader user hears "Inhale for four seconds" rather than nothing; text meets a 4.5:1 contrast ratio against its background, and several of the theme colours were changed specifically to reach it; prefers-reduced-motion is honoured, and with it set the circle holds one size while a ring drawn around its circumference carries the pace, with the per-second count and the progress bar still advancing; there is no flashing content anywhere, at any rate; every page has a skip link, one h1, headings that do not skip levels, and visible focus styles.

What is not claimed: there is no published WCAG 2.2 or EN 301 549 conformance statement, and there will not be one until an independent audit has been paid for and passed. A conformance claim is a legally operative statement, and making one without an audit behind it would be dishonest. If you need a Voluntary Product Accessibility Template or an accessibility conformance report for a procurement process, none exists.

If you hit an accessibility problem, email it to contact@helpmebreath.com. Accessibility bugs go to the front of the queue.

7. Support terms

  • Channel. Email, at contact@helpmebreath.com. There is no phone line, no live chat and no ticketing portal.
  • Response time. Within two business days. In practice it is usually faster, but two business days is the commitment, and it is one person's commitment rather than a rota's.
  • Hours. Business days are Monday to Friday, excluding public holidays in Lebanon.
  • What support covers. Activation problems, billing and refunds, embed and white-label setup, the handout pack, the compliance documents, and bug reports.
  • What it does not cover. Clinical or teaching advice about which pattern to use with whom, custom development, integration work on your own site, or a service level agreement with credits attached to it. None of those exists.
  • Uptime. No uptime guarantee is offered. The site is static and served from a CDN, which is about as resilient as a small site gets, and the timer keeps working offline once a page has been visited. But there is no SLA, and claiming one would be a promise the operation cannot keep.
  • Refunds. Fourteen days, unconditional, processed by the merchant of record. The full policy is in the terms of service.

8. Responsible disclosure

If you find a security problem, please report it. Email contact@helpmebreath.com with "Security" in the subject line, and include enough detail to reproduce it.

  • You will get an acknowledgement within two business days.
  • You will get an assessment, and a fix or a plan, within fourteen days for anything that puts data or money at risk.
  • Please give thirty days before publishing, or ninety if the fix needs a subprocessor to act. If a fix is taking longer than that, you will be told why rather than ignored.
  • Testing against your own browser, your own account and your own embed is welcome. Please do not run automated scanners against the hosting platform, do not attempt denial of service, and do not access or modify data that is not yours.
  • There is no bug bounty. There is no budget for one. What there is: a fast, honest reply, credit on this page if you want it, and a fix.

9. What this operation does not have

Listed here so nobody has to ask, and so nobody discovers it after paying.

  • No SOC 2 report, no ISO 27001 certificate, no penetration test report.
  • No HIPAA Business Associate Agreement. The product is not designed for protected health information and does not receive any.
  • No single sign-on, no SAML, no SCIM, no admin console, no audit log export.
  • No completed vendor security questionnaires. These three documents are the answer, and they are the whole answer.
  • No legal entity, no data protection officer, no security team. One person, in Lebanon, who answers his own email.
  • No 24/7 on-call, no incident status page, no service level agreement.

If any of that is a requirement for you, this is the wrong tool and it is better to know now. If none of it is, you have the whole picture, and the picture is unusually simple: a static site whose only stored personal data is your own account record, with nothing of your clients' in it.
